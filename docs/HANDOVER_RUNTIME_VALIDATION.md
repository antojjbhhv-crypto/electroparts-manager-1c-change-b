# Передача: Runtime Validation в полноценной 1С 8.3.27

**Кандидат:** ветка `audit-remediation`, коммит `af73010b09c954885339c3c008329b1b2231ddab`
**PR:** #1, OPEN, Draft; merge не разрешён до завершения этапа
**Дата:** 2026-11-21
**Связанные документы:** `docs/AUDIT_RUNTIME_REPORT.md` (разделы 1–9), `docs/SECURITY_REMEDIATION_ADDENDUM.md`

## 1. Цель и границы

Цель — выполнить рантайм-проверки 2–7 кандидата Security Remediation в полноценной 1С 8.3.27 и получить доказательства.

Не проверяется: конкурентность T-J/D10b, T14; инцидент MB; бизнес-логика вне изменений кандидата.

Кандидат не изменяется: `config-xml/DataProcessors/Korrektur/Ext/ObjectModule.bsl`, `config-xml/Roles/Korrektur/Ext/Rights.xml`, бизнес-логика и права.

## 2. Требования к платформе

- 1С:Предприятие 8.3.27, полная (не учебная) лицензия; версия 8.3.27.1508 или совместимая.
- Файловая информационная база на локальном диске (сервер 1С не обязателен).
- Толстый клиент, управляемое приложение.
- Права администратора для создания базы, пользователей и тестовых ролей.

## 3. Исходные артефакты

- Репозиторий: `antojjbhhv-crypto/electroparts-manager-1c-change-b`, ветка `audit-remediation`.
- Конфигурация кандидата — на коммите `af73010`; документы передачи добавлены поверх, `config-xml` не менялся.
- `config-xml/` — 29 файлов конфигурации.
- `MANIFEST_SHA256.txt` — в скачанном коммите; SHA-256 манифеста указан в сообщении коммита, которым он обновлён. На коммите `af73010` манифест содержал 108 записей с SHA-256 `d332d3e515f43df5c2b6d875d7260530e931b870ae7eb633c82de3dd6ddb7bf5`.
- Кандидат: `ObjectModule.bsl` — `8fbf81872ea85994a74a999beb73a0f8b4b0c56958c80388ba5397f220ea1382`; `Rights.xml` — `02535a6ec02bf8398c80b85a161e393f796a1a2579c1f05b356f9f88dc7a9067`.

## 4. Развёртывание

1. Создать пустую файловую информационную базу.
2. Конфигуратор → «Загрузить конфигурацию из файлов» → каталог `config-xml`; обновить конфигурацию базы данных.
3. `DESIGNER /CheckModules` — ожидается «Синтаксических ошибок не обнаружено!».
4. В тестовой копии конфигурации (не в ветке) создать роли:
   - `AuditFullAccess`: `Administration`, `DataAdministration`, `ExclusiveMode`, `UpdateDataBaseConfiguration`, `ThickClient`, `ThinClient`, `MainWindowModeNormal`, `MainWindowModeFullScreen`, `MainWindowModeKiosk`.
   - `AuditClientBase`: только `ThickClient`, `ThinClient`, `MainWindowModeNormal`, `MainWindowModeFullScreen`, `MainWindowModeKiosk`.
5. Создать пользователей (Администрирование → Пользователи):
   - `audit_admin` — `AuditFullAccess` + `Korrektur`;
   - `audit_korr` — `Korrektur` + `AuditClientBase`;
   - `audit_korr2` — `Korrektur` + `AuditClientBase` (нужен для теста 5.6).
6. Проверить, что загруженные `ObjectModule.bsl` и `Rights.xml` совпадают с хешами из раздела 3.

Важно: `Korrektur` не получает прав запуска клиента; `AuditClientBase` не получает бизнес-прав, прав на регистры и привилегированного режима.

## 5. Матрица пользователей и ролей

## 6. Предварительные проверки (до тестов)

1. Войти как `audit_admin`, открыть обработку `Korrektur`. Ожидается: раздел `Lager` виден, форма открывается.
2. Войти как `audit_korr`, открыть обработку `Korrektur`. Ожидается: форма открывается.
3. Зафиксировать скриншоты формы и путь команды.

Если форма не открывается хотя бы под одним пользователем — STOP: статус `BLOCKED`, сохранить ошибки и скриншоты, права не расширять.

## 7. Сценарии тестов

### Тест 2. Поведение роли

Под `audit_korr`: открыть `Korrektur`; прочитать остатки `Bestaende` и записи `KorrekturJournal` (запросом из пробы или через форму). Ожидается: чтение доступно, обработка доступна.

### Тест 3. Прямой запрет изменения регистров

Под `audit_korr` запустить тестовую пробу (Приложение A). Ожидается отказ платформы:
- прямая запись в `InformationRegister.KorrekturJournal`;
- прямая запись набора записей в `AccumulationRegister.Bestaende`.

Данные не должны измениться. Пробу выполнять только от имени `audit_korr`, без привилегированного режима.

### Тест 4. Контролируемая запись журнала

Под `audit_korr` выполнить корректировку через форму: UUID1, компонент, изменение `+1`, причина. Ожидается: запись `KorrekturJournal` создана и обновлена до `Проведено`, `OperationID` совпадает, документ создан и проведён. Снять журнал до и после.

### Тест 5. Идемпотентность и полный payload

Каждый сценарий — отдельный результат:

| № | Действие | Ожидается |
|---|---|---|
| 5.1 | Новый UUID, корректный payload | операция проходит, документ создан |
| 5.2 | Тот же UUID, полностью идентичный payload | возвращается исходный документ, новых документов и движений нет |
| 5.3 | Тот же UUID, другая компонента | отказ, без новых документов и движений |
| 5.4 | Тот же UUID, другое количество | отказ |
| 5.5 | Тот же UUID, другая причина | отказ |
| 5.6 | Тот же UUID и payload, пользователь `audit_korr2` | отказ |

Для каждого отказа проверить: запись журнала не повреждена, исходный документ и payload сохранены.

### Тест 6. Восстановление привилегированного режима

- A (успех): проба фиксирует `ПривилегированныйРежим()` до и после успешной корректировки — ожидается `Ложь` / `Ложь`.
- B (ошибка): повтор с тем же UUID и изменённым payload вызывает ошибку записи в helper; после исключения `ПривилегированныйРежим()` — `Ложь`, исключение не скрыто.

### Тест 7. Регрессия T-F

В отдельной копии тестовой конфигурации вставить `ВызватьИсключение "T-F: принудительный сбой записи журнала";` перед финальной записью журнала (после проведения документа). Под `audit_korr` выполнить корректировку с новым UUID. Ожидается: ошибка, откат транзакции — документа нет, движений нет, записи журнала нет, остатки не изменились.

## Приложение B. Проверка манифеста

```powershell
$man = "MANIFEST_SHA256.txt"
$bad = 0
Get-Content -LiteralPath $man -Encoding UTF8 | Where-Object { $_.Trim() } | ForEach-Object {
    $parts = $_ -split '\s{2,}', 2
    $h = $parts[0].Trim().ToLower()
    $rel = $parts[1].Trim()
    if ((Get-FileHash -LiteralPath $rel -Algorithm SHA256).Hash.ToLower() -ne $h) { $bad++ }
}
"bad=$bad"
(Get-FileHash -LiteralPath $man -Algorithm SHA256).Hash.ToLower()
```
